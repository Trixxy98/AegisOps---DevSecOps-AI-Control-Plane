# 14 — DevOps & Infrastructure

## 1. Local / demo topology (Docker Compose)

```
docker compose up -d                      # core: postgres, redis, migrate, api, worker, web
docker compose --profile ai up -d         # + ollama, ollama-init
docker compose --profile observability up -d   # + prometheus, grafana
docker compose -f deploy/docker-compose.targets.yml up -d   # target networks + latest target images
```

## 2. Dockerfiles

### API / Worker (multi-stage)

```dockerfile
FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build
WORKDIR /src
COPY Directory.Build.props Directory.Packages.props AegisOps.slnx ./
COPY src/ src/
RUN dotnet restore src/AegisOps.Api/AegisOps.Api.csproj
RUN dotnet publish src/AegisOps.Api/AegisOps.Api.csproj -c Release -o /app --no-restore

FROM mcr.microsoft.com/dotnet/aspnet:10.0-alpine AS runtime
WORKDIR /app
RUN adduser -D -u 10001 aegisops
COPY --from=build /app .
USER aegisops
EXPOSE 8080
HEALTHCHECK CMD wget -qO- http://localhost:8080/health/live || exit 1
ENTRYPOINT ["dotnet", "AegisOps.Api.dll"]
```

Worker identical with its project; Worker runtime image additionally needs the Docker
socket group id matched (`--group-add` via compose `group_add`).

On a Mac host the socket is `unix://${HOME}/.docker/run/docker.sock`, not
`/var/run/docker.sock`. Set `DOCKER_HOST` (or `Docker:Endpoint`) to that path.
Mounting the raw socket into the Worker is equivalent to root on the host. Prefer a
[docker-socket-proxy](https://github.com/Tecnativa/docker-socket-proxy) sidecar that
allows only `CONTAINERS=1`, `IMAGES=1`, `NETWORKS=1`, and keep `POST=1` for create/start.
Point `DOCKER_HOST` at `tcp://docker-socket-proxy:2375` and do not mount the socket
into the Worker.

## 3. GitHub Actions — AegisOps repository

### `ci.yml` (on PR and push to `main`)

```
backend:   dotnet restore → build (warnings as errors) → test (unit + architecture)
           → integration tests (Testcontainers; docker available on ubuntu runners)
           → coverage report (coverlet → Codecov-free summary in job output)
frontend:  npm ci → lint (eslint) → typecheck (tsc) → gen:api drift check → vitest → build
security:  gitleaks (SARIF → GitHub code scanning) · semgrep (SARIF) · trivy fs (SARIF)
images:    on main only — build api/worker/web → trivy image scan → push to GHCR with :sha and :latest
```

Fail conditions: any test failure, lint/type errors, **Critical** finding in Trivy/Gitleaks
(dogfooding the same threshold as the Production baseline).

### `release.yml` (on tag `v*`)

Builds and pushes versioned images, generates release notes (conventional commits),
attaches `deploy/sql/migrate.sql` for review.

### `dependabot.yml`

Weekly for `nuget`, `npm`, `docker`, `github-actions`.

## 4. GitHub Actions — target repositories

Documented in [13 Target applications §4](13-target-applications.md#4-template-repository-layout).
Sequence recap:

```mermaid
flowchart LR
    A[push / tag] --> B[build + test]
    B --> C[docker buildx → GHCR<br/>output: image, digest]
    B --> D[gitleaks · semgrep]
    C --> E[trivy image]
    C & D & E --> F[POST /artifacts]
    F --> G[POST /artifacts/:id/scans ×3]
    G --> H{branch/tag?}
    H -- main or vX.Y.Z --> I[POST /deployments → Staging]
    H -- workflow_dispatch Production --> J[POST /deployments → Production]
```

A small **composite action** in the AegisOps repo (`.github/actions/aegisops-report`) wraps
the `curl` calls so target workflows stay short:

```yaml
- uses: <owner>/AegisOps/.github/actions/aegisops-report@v1
  with:
    url: ${{ vars.AEGISOPS_URL }}
    api-key: ${{ secrets.AEGISOPS_API_KEY }}
    project: circuit-service
    version: ${{ steps.meta.outputs.version }}
    commit-sha: ${{ github.sha }}
    branch: ${{ github.ref_name }}
    image: ${{ steps.build.outputs.image }}
    digest: ${{ steps.build.outputs.digest }}
    test-summary: test-summary.json
    scans: gitleaks.sarif,semgrep.sarif,trivy.sarif
    deploy-to: Staging
```

Run this step only after the build, tests and scanners succeed. Give its project-scoped
API key `artifacts:write`, `scans:write`, and `deployments:request` scopes; save the
one-time plaintext as a GitHub Actions secret. The runner needs `bash`, `jq`, and `curl`.
`test-summary` is optional (omitted means no summary, **not** fabricated passing tests);
`digest` is optional for Staging. Supplied summary and SARIF paths must exist. The action
registers the artifact, uploads the named reports, then requests Staging; a failed upload
stops the request. Artifact/deployment requests use run-attempt idempotency keys, so
retrying the same attempt does not create another deployment. Scan uploads are **not**
idempotent and may be repeated on retry. Verify the run in the project's deployment list;
an accepted request can later be denied by policy or fail in the worker.

To test the action payloads without a server or credentials, run
`bash tests/report-action.sh`. This mocks HTTP; it does not exercise API authorization
or the deployment worker.

The sibling `aegisops-circuit-service/.github/workflows/ci.yml` already has a `register`
job using this action at `@dev`. Local tests of that repository and an isolated AegisOps
Compose run verify the report/scan/request contract, but a real GitHub Actions run requires
the action changes to be committed on the referenced branch, a reachable `AEGISOPS_URL`,
a project-scoped `AEGISOPS_API_KEY` secret, a self-hosted runner for `register`, and a
published image. No push or live GitHub run is performed by the local verification.
The demo branch's scan fallbacks and fixed passing test summary are not evidence of a
successful security scan or test run; do not use that workflow as a production gate.

### Reaching AegisOps from GitHub-hosted runners

AegisOps runs on a laptop in the demo. Options, in order of preference:

1. **Self-hosted runner** on the same machine/network (free, simple; GitHub Actions
   `runs-on: self-hosted`) — used for the `register`/`deploy` jobs only; build/scan jobs
   stay on GitHub-hosted runners.
2. **Tunnel** (Cloudflare Tunnel free tier / `ngrok` free) exposing `api` over HTTPS with
   an allow-list on `/api/v1/projects/*/artifacts`, `/artifacts/*/scans`, `/deployments`.
3. Offline fallback: `scripts/ci-replay.sh` re-plays saved artifact JSON and a Staging
   request into a local AegisOps (requires a pre-existing project and API key). It does
   not upload SARIF reports, so the seeded Staging scan policy can deny execution.

   ```bash
   AEGISOPS_URL=http://localhost:8080 AEGISOPS_API_KEY="$CIRCUIT_SERVICE_API_KEY" \
     bash scripts/ci-replay.sh tests/fixtures/ci-payloads/circuit-service.json
   ```

   Re-running the same fixture returns the same artifact and deployment response. To
   simulate a new CI version, change both the version and image reference in a copy
   of the fixture. This path does not require the original seeded admin password, but
   obtaining a project key still requires an authorized project owner/admin.

## 6. Configuration & secrets management

- Layering: `appsettings.json` → `appsettings.{Environment}.json` → env vars → user-secrets
  (dev). Options validated with `ValidateDataAnnotations().ValidateOnStart()`.
- Secrets never in images or Git; Compose reads `.env`; production-like uses Docker
  secrets/files (`Jwt__SigningKey__File` support via a tiny config provider).
- `scripts/gen-secrets.sh` creates `.env` with random JWT key, DB passwords, Grafana admin.

## 8. Release & versioning

- AegisOps: SemVer tags; `CHANGELOG.md` generated from Conventional Commits.
- Images: `ghcr.io/<owner>/aegisops-api:{version|sha|latest}` (same for worker/web).
- Database: migrations are forward-only; a down-migration is only used in development.
