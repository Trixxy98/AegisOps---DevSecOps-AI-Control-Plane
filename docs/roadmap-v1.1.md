# Roadmap — v1.1: production readiness

v1.0 is for evaluation and demos on one machine (see README, "Intended use and limits"). v1.1 makes AegisOps
something another team can run for real. Estimates are working days for one developer.

| # | Item | Why | Estimate |
| --- | --- | --- | --- |
| 0a | **Environment configuration and secrets.** Per-environment variables (plain or secret) set by team Owners/Admins, secrets encrypted at rest and write-only in the API, injected into the container at deploy time, audited without values | Almost every real application needs a connection string or API key; today a deployed container only receives `ASPNETCORE_ENVIRONMENT` | 1.5–2 |
| 0b | **Self-service onboarding.** "Create project" in the UI, a "connect your repository" guide with copy-paste GitHub Actions and plain-curl (GitLab, others) examples, the report action published as `@v1` — **Done**: "Create project" form on the Projects page, [connect-your-repository.md](connect-your-repository.md), `examples/github-actions/`, the action README, and the `v1` tag of the report action is published | Other people cannot connect their own repositories without help today | 1–1.5 |
| 1 | **Production profile.** `docker-compose.prod.yml` with `ASPNETCORE_ENVIRONMENT=Production`, a one-shot `migrate` command or init container (migrations are refused outside Development today), no demo seed — **Done**: `deploy/docker-compose.prod.yml` (Production for api/worker, no auto-migration, Postgres/Redis unpublished, restart policies, `migrate` service in profile `tools`); API commands `migrate` (migrations + roles via `IdentityRoles.EnsureAsync`) and `bootstrap-admin`; startup refuses the `.env.example` JWT key and the Development database password outside Development; guide [deploy-production.md](deploy-production.md) | AegisOps cannot start outside Development mode | 1 |
| 2 | **First-admin bootstrap.** `aegisops admin create --email …` (or env-driven, single use) that creates the first Admin with a temporary password; audited — **Done**: `docker compose … run --rm api bootstrap-admin --email … [--display-name …]`; refused once any Admin exists; random temporary password printed once, `MustChangePassword`, audit `user.bootstrapped` (System, `bootstrap-admin`). **Follow-up done (user management):** `POST /api/v1/admin/users` (temporary password shown once, optional team membership), `PATCH /api/v1/admin/users/{id}` (rename, activate/deactivate with refresh-token revocation) and `PUT /api/v1/admin/users/{id}/roles`, with guard rails (no self-deactivation or own-Admin removal, the last active Admin is kept) and audit `user.created/updated/deactivated/activated/roles_changed`; Administration → Users has Add user, Activate/Deactivate, Edit roles and Reset password | Without the Development seed there is no way to create the first user | 0.5 |
| 3 | **TLS and reverse proxy guide.** Caddy/nginx example with HTTPS and HSTS; `UseForwardedHeaders` with a known-proxy list so client IPs (rate limits, audit) are correct — **Done**: `deploy/docker-compose.tls.yml` + `deploy/caddy/Caddyfile` (automatic certificates, HTTP→HTTPS, HSTS, only 80/443 published); opt-in `ForwardedHeaders:*` (known networks/proxies, hop limit) before logging/auth/rate limiting; nginx passes `X-Forwarded-For`/`-Proto` and accepts 20 MiB scan uploads. **To verify live:** certificate issuance on a real domain and the Caddy image tag | Today all browser users share nginx's IP and traffic is plain HTTP on loopback | 1 |
| 4 | **Rate limits per principal.** Global limiter partitioned by user or API key, an `uploads` policy for scans, `Retry-After` headers — **Done**: `ApiRateLimiting` — global token bucket per JWT `sub` / API key id / client IP (anonymous) on `/api` (300, 50 per 10 s) and a separate bucket on `/hubs`; health and metrics unlimited; `uploads` policy on scan uploads (30, 5 per 10 s); `auth` unchanged (10/min per IP); all configurable under `RateLimits:*`; every 429 is Problem Details with `Retry-After` (`RateLimitingTests`). Left: limits are in memory per API instance (fine for one instance; a Redis-backed limiter would be needed to scale out) | Only login/refresh and AI are limited (docs/17) | 0.5 |
| 5 | **Errors as Problem Details.** `AddProblemDetails` + `UseExceptionHandler` with `traceId`; no developer exception page in the production profile — **Done** (all environments; tested in `ProductionHostingTests`) | Unhandled errors return empty 500s or stack traces | 0.5 |
| 6 | **Audit tamper protection.** Separate database roles: the app may only `INSERT`/`SELECT` on `audit.*` — **Done** for the production profile: `migrate` (owner) creates/updates the LOGIN role `aegisops_app` from `APP_DB_PASSWORD` (`AppDatabaseRole`, idempotent, default privileges for future tables); api and worker connect as it; no code updated or deleted audit rows. `scripts/gen-secrets.sh` generates the password (`--upgrade` adds it to an existing `.env`). **To verify:** `AppDatabaseRoleTests` against a disposable PostgreSQL (`AEGISOPS_TEST_POSTGRES`) and one live upgrade (`migrate`, then `up -d`). Left: Development still uses the owner; the API does not check its own role at startup; integrity is role-based, not cryptographic (V2 hash chain) | docs/17 §2 promise not yet implemented | 0.5 |
| 7 | **Regex hardening and stored-AI-content encryption.** `NonBacktracking` + timeouts for policy globs and AI blocked patterns; Data Protection column encryption for `prompt_content`/`response_content` — **Done**: branch globs (`BranchGlob`) and blocked patterns (`AiBlockedPatterns`) compile with `NonBacktracking`, `CultureInvariant` and a 100 ms timeout, are validated on policy save (400 Problem Details: empty/too long/too many, invalid syntax, backreferences/lookarounds/atomic groups) and fail closed at evaluation (AI: 503 `PolicyInvalid`; branches: deny). Stored content uses the existing AES-256-GCM key-ring pattern instead of Data Protection: new `AiContent` ring (api only; AAD = request ID + column), `AI_CONTENT_*` in Compose, `gen-secrets.sh` (and `--upgrade`), `.env.example`; without a key nothing is stored and `content_skipped` is set (migration `AiContentSkipped`); rotation in [operations.md §5.6](operations.md#56-stored-ai-content-encryption-keys-ai_content_). Tests: `BranchGlobTests`, `AiGatewayTests` (save validation, catastrophic inputs, timeout, round trip, AAD, not configured), policy save 400s in `ProjectAndPolicyEndpointTests`. Left: plaintext rows from before the upgrade are not re-encrypted (they expire with retention or can be cleared with the documented SQL); no endpoint reads stored content back | docs/17 §3, §5 | 1 |
| 8 | **Bring your own repositories.** Target-repo workflow and `aegisops-report` action documented for any GitHub owner (no `Trixxy98` references), versioned action tag (`@v1`) instead of `@dev` — largely covered by 0b (owner-independent example workflow, action README, `@v1`); the demo target repositories still use `@dev` | Others cannot reuse the CI integration as-is | 1 |
| 9 | **Operations guide.** Backup/restore (`pg_dump`), upgrades and migrations policy, secret rotation (JWT key ring, webhook keys), sizing — **Done**: [operations.md](operations.md) (state inventory, backups with off-host copies, encryption at rest and cron, restore and quarterly drill, upgrades and rollback, forward-only migration policy, rotation of the JWT key, webhook and environment-secret key rings, database passwords and API keys, health/logs/disk housekeeping, sizing estimates, troubleshooting); `scripts/backup.sh` (`pg_dump` custom format, read-only tar of the `reports` volume, manifest with migrations and row counts, SHA-256 checksums, umask 077, never reads `.env`); `scripts/restore.sh` (checksum verification, typed confirmation, restore into a temporary database swapped in only after `pg_restore` and row counts succeed, reports volume, `migrate` in production, readiness wait; `--verify-only` into a throw-away container); `deploy/docker-compose.drill.yml` for an isolated drill (own network, no Worker); `key2` slot for environment secrets in Compose. Verified live on 2026-11-12 (Development stack): backup of 18 migrations / 35 tables / 3,225 rows with matching SHA-256 checksums, `--verify-only` row counts matched, the shared-network guard refused an unsafe drill, and an isolated `aegisops-drill` restore (temporary database swap, reports volume, readiness 200) matched the backup row counts and report files. Release rehearsal on 2026-11-12 with the published v1.1.0 images (arm64 pulled natively) in an isolated project with the production and TLS overlays: `migrate`, `bootstrap-admin`, HTTPS through Caddy (`https://localhost`, HSTS, HTTP→HTTPS 308), forced password change, users and team created, auth rate limit 429 with `Retry-After`, then `backup.sh --tls` → change → `restore.sh --tls` restored the data, re-ran `migrate`, and `aegisops_app` still could not UPDATE/DELETE/TRUNCATE audit rows. Left: JWT key ring (one key; rotation signs everyone out), no automatic re-encryption of environment secrets, no point-in-time recovery | Running it for months needs this | 1 |
| 10 | **CI scope.** Semgrep `p/owasp-top-ten` with `--error`, `npm audit --audit-level=high`, `dotnet list package --vulnerable`; multi-arch images (amd64 + arm64) — **Done**: Semgrep adds `p/owasp-top-ten`; instead of `--error` (which fails on every severity) the SARIF keeps all findings and a final gate step fails on SARIF level `error` (Semgrep ERROR); `npm audit --audit-level=high --omit=dev` (runtime dependencies only); `dotnet list package --vulnerable --include-transitive --format json` fails on any listed package (restore-time NuGet audit stays on); `release.yml` adds QEMU (SHA-pinned), scans the loaded amd64 image with Trivy, then pushes linux/amd64 + linux/arm64; Dockerfile build stages run on `$BUILDPLATFORM`. **To verify:** the first CI run with the new gates (p/owasp-top-ten may report findings that were never scanned before) and the first multi-arch release tag, plus one local `docker compose build`. Left: the arm64 image is not scanned separately; no image scan on pull requests | docs/17 §7 | 0.5 |

**Total: about 10–11 days.** Items 0a–0b make AegisOps usable as a third-party deployment gate for other people's
applications and come first. Items 1–3 are the minimum for a team to self-host behind HTTPS; 4–7 close the
remaining v1 security-review items; 8–10 make it maintainable and reusable.
